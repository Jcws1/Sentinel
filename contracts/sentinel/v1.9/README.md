# Contract package 1.9 — D3a saved missions, completion dependencies and live boundaries

Deploy backend and frontend together. World/stream **1.8**, interactive/status **1.5**, command receipts **1.4**, checkpoint **1.5** and dependency scenario/review **1.3** coordinate this release. SQLite stays **4**: existing immutable JSON revision, receipt, frame, event and checkpoint tables suffice. No application dependency or structural storage migration is added. Packages 1.0–1.8 remain unchanged.

`local-schedule-v2` supports either `offsetMs` or `afterActionId` plus `delayMs`. Dependencies are same-actor linear chains with stable IDs, no branches/cycles/dangling references, at most 128 actions and 200 ms increments. Existing absolute-only content keeps its 1.2 format and `local-schedule-v1` behavior. Copies remap actors, actions and predecessors before journalling one exact request. Save/review/Run retain their existing owners and authoritative admission.

A successful committed completion makes its successor eligible at `completionTick + max(1, delayMs / 200)`. Fixed-time dispatch wins a same-actor collision; the dependent start is skipped with a reason. Failed, skipped, cancelled and interrupted predecessors skip their dependent chains. New starts end at tick 3000; unfinished dependent starts are visibly skipped afterward, while already-running motion may finish. Pause freezes the source clock. Stop/Move override, Return eligibility and restart interruption remain authoritative; no wall-clock scheduler, arrival estimate disguised as a trigger, group barrier or automatic replay is introduced.

`boundary-edit` is a fresh nonpositional, source/run/epoch/grant-bound leased command. Its mutation carries `expectedRevision`, operation, run-qualified boundary ID and an upsert definition (or no geometry for Delete). Untyped geometry stays local/provisional. CAS rejects conflicting changes; accepted receipts identify `boundaryRevision`. Exact request retries use the same immutable receipt owner.

The original scenario snapshot stays immutable. `liveBoundaries` identifies the current effective rule revision, source/run, last command and committed sequence; ordinary Zones and `boundaryRules` represent the effective set. Boundary events, affected movement outcomes, checkpoint and world state commit atomically before publication. Restricted activation refuses source-owned occupied/unknown-position footprints; accepted changes fail crossing *remaining* movements at their committed positions. Subsequent manual and script admission/steps use the effective rules, even with overlays hidden. Deletion never restarts failed work. Restart and recorded frames preserve the effective set. Friendly and Patrol retain their disclosed future semantics; no engagement or automatic patrol engine exists.

Missions exposes latest saved definitions separately from instantiated runs. Loading a definition creates no recording. Explicit Run pins its revision/hash and creates fresh identities through the same ready/acquire/start lifecycle. `sentinel.scenario` mission display metadata associates the originating arrangement/revision with the existing demo alias; legacy projection may derive it from the immutable saved run snapshot without rewriting historical bytes.

Strict legacy models validate old world, schedule, scenario and receipt versions before in-memory adaptation. Source specifications, hashes, stored profiles, earlier frames and receipt bytes are unchanged.
