## 1. Operator experience and verified starting point

The operator opens **Units**, places friendly drones, hostile drones and unknown entities on the existing map, draws typed boundaries, then uses **Conductor** to add a short list of timed movements. **Run scenario** freezes a saved scenario revision into a fresh demo recording. During the run, hostile entities follow the script and remain inspectable; explicitly controlled friendly assets accept live commands from the map and Fleet. Fleet provides one compact behavior control for Hold, Patrol and Intercept. A small deterministic coordinator assigns distinct targets, retains spare interceptors and records a clearly simulated mutual-loss result. Details can open a simulated cockpit. Conversational option cards help the operator choose the next action; applying an option always uses the normal validated command path.

The map remains dominant. Units and Conductor are workbench views, not separate applications. Scenario authoring, running and recorded inspection are visibly distinct contexts. The existing quick **New demo** remains a one-click preset workflow; **Run scenario** is the deliberate custom-arrangement workflow.

## 3. Interaction and UI specification

### Boundaries and gesture coexistence

Add **Draw zone/boundary** beside existing Pan, Move and Recenter controls, retaining Select. One session-owned authoring tool is armed in one map pane at a time; cameras remain pane-local. Draft vertices are UI data, never an authoritative live Zone.

1. In a scenario draft, select Draw and left-click vertices. Show a neutral outline and rubber-band edge with vertex count and brief keyboard help.
2. Double-left-click contributes one final distinct vertex and closes the polygon. Consume the component click events so the final vertex is not duplicated; suppress native double-click zoom only while drawing. Require at least three distinct vertices and nonzero area. Enter/Finish provides the same completion path.
3. A completed polygon remains **Untyped boundary**, grey with a dashed outline and label. It imposes no behavior until assigned a type. A draft may save untyped boundaries; Run validation requires typing or explicitly retaining each as annotation-only.
4. Right-click inside the polygon while in scenario authoring opens a compact menu: Friendly, Patrol, Restricted; then Rename, Edit vertices, Delete. Overlap opens a short labelled zone chooser first, ordered by stable ID, not arbitrary renderer feature order. Provide the same menu from a keyboard-accessible boundary list.
5. Edit mode exposes drag handles, selected-vertex Delete and Apply/Cancel. Allow vertex removal down to three; adding vertices can be deferred, because redraw is available. Invalid edits remain a draft and do not replace saved geometry. Retype, rename and whole-zone deletion are basic initial features; no freehand tool, holes, multipolygons or general GIS editor.

| Context | Click/drag behavior |
| --- | --- |
| Ordinary live Pan/Select | Existing click inspection, modifier selection, Select rectangle and native Pan drag remain. Right-click remains direct movement, including inside zones. Right-drag is always camera rotation/orbit. |
| Draft Draw/Edit | Left-click adds/selects a vertex; it does not select a unit or start a movement. Right-click on a completed area opens its menu; during an incomplete ring it offers Finish/Cancel and cannot move units. |
| Draft Units placement or Conductor destination pick | Explicit tool owns the next valid left-click. Right-click cancels that pick or opens its tool menu, never issues a live command. |
| Explicit Move destination tool | Destination intent wins over polygon context. A zone never makes its interior impossible to address; backend rules still validate the move. |
| Shared camera gestures | Keep the existing 5 CSS-pixel drag threshold, including a drag that returns to its start. Space temporarily pans, scroll zooms and right-drag orbits. A drag cannot finish a polygon, open a menu or send a command. |
| Cancellation/lifecycle | Escape cancels the active edit/pick before selection. Blur/lost capture suspends unfinished pointer gestures. Mission/draft change, pane disposal or tool switch exits authoring safely; retain saved geometry and require explicit return to any unsaved draft. Switching projection cancels the active pointer gesture, preserves completed draft vertices and requires rearming that pane. |

The right-click menu is deliberately contextual to **scenario authoring**. In a running scenario, boundaries are inspectable through the boundary list or an explicit Inspect boundary tool; the menu is read-only with **Edit next revision**. This preserves RTS right-click movement and makes the conflict visible rather than guessing from nearby entities.

Both Tactical and 3D can author the same horizontal vertices. Tactical uses geographic unprojection. 3D reuses the reviewed actual-surface picking guard: no sky pick, unsettled photorealistic geometry or hidden-globe substitution; picked surface height never becomes operational height. On a failed pick show why and offer Tactical/numeric entry without changing another map's camera. Provide numeric vertex entry and a Finish button for keyboard operation.

Display Friendly with a blue-green solid edge plus **FRIENDLY · NO ENGAGEMENT**, Patrol with a cyan dashed edge plus loop icon/**PATROL**, Restricted with amber hatching/double edge plus **RESTRICTED · NO ENTRY**. Keep neutral selection outlines separate from affiliation colors. The labels and line treatments convey meaning in grayscale. In 3D draw surface footprints with equivalent labels; do not invent extruded altitude limits. Disclose **horizontal rule at all demo heights** in the zone inspector. Terrain draping and visible polygon fill are presentation, not the rule evaluator.

### Boundary behavior

Authoritative checks use the existing local metric coordinate frame, a documented numerical tolerance (proposed 1 mm), and inclusive polygon edges. Validate simple closed non-self-intersecting rings, limits and extent on the backend. The frontend may preview validity but cannot admit geometry or movement.

| Case | Rule |
| --- | --- |
| Friendly boundary | Movement and patrol are allowed, but no autonomous attack may begin or resolve with either participant inside/on the boundary. A pursuit stops outside the protected area rather than following a protected target into it. No area-effect model exists. |
| Restricted boundary | No scenario-owned drone may start inside, enter, touch or cross the area. Check the whole movement segment, not just its destination. Reject an invalid replacement atomically, leaving its previous valid action intact. No silent rerouting or teleportation. |
| Patrol boundary | Assign selected controlled friendlies to one named area in Fleet. Use a deterministic clockwise loop through a validated inset of its convex vertices; stable starting waypoint by asset ID. Enter via a valid straight segment if outside; then repeat until Stop, replacement, loss or End. While assigned Patrol, all patrol segments remain inside/on its allowed patrol area and outside Restricted. This is an automatic loop, not separation control. |
| Overlap | Restricted always wins for movement. Friendly always vetoes engagement, even inside Patrol. Patrol restricts only its assigned members' patrol behavior. Multiple patrol zones never merge implicitly; each asset names one. No zone grants authority. |
| Already inside | Friendly occupants remain, with engagement blocked. Units already in Patrol can begin the loop. Run validation rejects restricted occupants; the operator repositions them in the draft. If inconsistent restored state is discovered, mark the drone blocked at its recorded position and require an explicit correction/new run; do not claim it is outside. |

### Fleet policy control and execution priority

Place one compact control at the top of the existing Fleet list: selected/eligible counts, a **Behavior** select, a policy-specific parameter field, **Apply**, and **Stop selected**. Policies: Manual/Hold, Patrol(boundary), Intercept(target scope, one-per-target), and Return to script. Show mixed selection honestly; explicitly list unavailable/skipped members. Activity retains per-execution cancellation/audit.

**Stop selected** obtains fresh backend intent and captures the exact selected member identities, relevant authority and per-member ordering context. It cancels those members' current actions, releases assignments, disarms autonomous policy, holds at last committed position and enables manual override so a later script action cannot restart them. It works while paused and needs no fresh geographic position. It is not End or a rollback. The existing execution-specific Cancel remains narrowly tied to its execution; late Cancel cannot touch a replacement.

Applying a policy that starts motion or engagement requires a running, healthy source and current positional admission evidence. Initial policies can instead be authored in the definition before Start. Hold/Stop and Return to script use fresh nonpositional intent, remain available while paused and never advance source time. An unavailable position may prevent motion while still permitting an authorized Stop; the UI must distinguish these reasons.

Priority is evaluated under the mission lock:

1. Terminal/non-operational state, explicit revocation/End and mandatory boundary/authority checks veto all movement or engagement. Pause suspends execution without revoking it.
2. Accepted Stop establishes Hold and prevents scheduled/autonomous restart. A later explicit valid operator command may release Hold; a delayed older command may not.
3. The newest valid operator intent for a member supersedes its prior work and script entitlement, within all hard rules.
4. An enabled Conductor action controls a member only without manual override; later valid script actions may replace earlier script actions.
5. Autonomous patrol/approach follows the accepted policy and scope; it cannot supersede a newer manual intent, stop or zone veto.

Extend per-asset logical ordering across new manual movement, policy Apply, Stop and Return-to-script requests. Keep existing direct-order high-water marks and legacy receipt semantics; do not reset order on a panel change or allow separate clients per tab. Freeze member/scope identities before asynchronous work. A skipped or rejected command does not consume a reservation or advance an accepted order. Accepted outcomes and current frame state remain separate.

### Simplified approach, engagement and reserve cycle

The minimum workflow is **select interceptors → choose Intercept in Fleet → select one or a group of hostile targets on the map/list → Apply**. The target-pick tool fills a separate target-scope field without replacing the friendly participant selection or creating another primary history owner; ordinary inspection still uses shared selection. Interceptors approach their assigned moving targets and resolve automatically. There is no separate detonate or pair-loss click. An **Intercept on approach** setting also arms the same policy for map movement: an explicitly armed right-click on a hostile, or within a disclosed 250 m notional acquisition area around selected hostile targets, captures an approach-and-engage intent. The tool cursor/acknowledgement must say **Intercept**, and scope IDs are frozen in the request. An ordinary unarmed ground Move stays a movement command. This distinction is a material default; a hidden global auto-attack behavior is excluded.

Recommend delivering the direct Fleet target-pick workflow first within D4, then the armed map shortcut before D7. A plain manual ground redirect while pursuing terminates the assignment and returns that member to Manual; it cannot be immediately pulled back by an old intercept policy. To approach another enemy, explicitly use the Intercept policy/shortcut again. Policies never derive target eligibility from what filters happen to show.

Use a versioned **`demo-mutual-loss-v1`** rule with these disclosed assumptions:

- Only operational, located, fresh, same-run/source hostile targets explicitly within the accepted target scope are eligible; Unknown/Neutral, observation-only external sources and other runs are excluded. Friendly interceptors need both movement and demo-intercept capability plus the run's demo-outcome capability.
- Each 0.2-second step steers directly toward the target's latest committed horizontal position at the persisted preset speed, preserving each entity's supplied ellipsoid height. No acceleration, turn radius, lead calculation, prediction, obstacle avoidance or validated pursuit model.
- The proposed toy trigger is minimum separation **at most 25 m** during a step in local `(x, y, ellipsoid height)` coordinates. Check the relative swept segment of the two proposed motions so a discrete step cannot jump over the trigger. All default engagement fixtures share an altitude; no vertical interception is implied. Freeze radius, equality/tolerance and algorithm version in the run profile; the number has no real-world effects meaning.
- Clip/stop invalid motion before testing effects. At the first eligible candidate contact fraction both participants must be outside Friendly and Restricted boundaries; pursuit steps through protected areas are blocked. Freeze consumed participants at those calculated evaluation positions and record the within-step fraction alongside the committed tick; this is part of the toy calculation, not an observed physical collision. Evaluate all candidate motions from the same pre-step state, order any competing outcomes by stable assignment ID, reserve participants once, then commit the final frame. Database failure advances neither movement, assignments nor outcomes.
- In one transaction, mark both Entities `condition=non-operational`, retain affiliation and `presence=present`, set affected Asset availability unavailable, cancel unfinished execution with `simulated-loss`, release assignments, cancel their future scheduled movements, and append an outcome with pre/post state, algorithm/profile, input frame/tick, command/policy/assignment IDs and evaluation positions. Completed executions remain Completed. Other members continue.
- Keep destroyed/non-operational entities at the recorded simulation position with supplied zero speed and continuing stationary source observations while running. No falling, wreckage placement, terrain snap, radius blast, damage probability or propagation to bystanders. Restart and replay reads preserve the committed result exactly once.

Show a brief restrained engagement cross/burst, approximately 600 ms, labelled **SIMULATED ENGAGEMENT**. Reduced motion uses a static acknowledgement. Anchor it to recorded evaluated positions; do not animate an invented physical explosion. Persist grey/slashed NON-OP symbols with affiliation outline/shape and accessible labels after the cue disappears. Condition is distinct from stale, disconnected, ended Track, unlocated or filtered. Add a shared condition filter defaulting to all; Fleet never silently drops losses. A reconnect shows persistent outcome/state without replaying old transient cues as new events.

Use a deterministic allocator, not an AI model: preserve valid existing assignments; sort candidate pairs by current local distance, then stable target/asset IDs; greedily admit unused members/targets only when zone and control checks pass. This is reproducible, not claimed globally optimal. Persist assignment IDs/revisions and release reasons. Never reshuffle valid assignments on every frame.

| --- | --- |
| 10 eligible friendly interceptors, 10 eligible hostile drones | Ten unique assignments, one friendly per target, assuming all are reachable under the declared simple rules. No accidental duplicate targeting. |

This supplies an observe–orient–decide–act loop: inspect committed results → see remaining targets and reserves → choose Hold or Allocate reserves → issue a new validated intent. Coordinated spacing, formation keeping, communications, consensus, optimization, pursuit prediction, automatic multi-wave dispatch and multi-interceptor simultaneous effects remain later work.
